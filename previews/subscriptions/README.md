# Phase 3C.3A — Unpublished form preview and publication gates
Owner approved development/testing only. No public route changes, production writes, delivery, services or purchases. This branch is NOT a live site. Preview requires a local static server; use fictional details only. Never merge preview assets into a publicly deployed branch before approval.
## Implemented in this draft
- Independent email and SMS choices, separate unchecked consent, adult confirmation, exact nine existing subscription topics, normalized contact destinations, pending-only request model; no inquiry auto-subscription.
- Preference access request validation only. No account lookup, enumeration, preference mutation or token delivery. UI never claims a successful subscription.
- Offline preview with restrictive CSP, no outbound requests or persistence. Draft wording requires review against applicable law and final privacy policy, terms, provider registration and actual capabilities. STOP/HELP language describes proposed future service, not an available service.

2. Implement and test a bounded server-only request transaction: validate exact allowlist against active DB topics, independently validate consent and adult declaration, derive consent text/version server-side, atomically create only pending records and requested consent events, protect existing active/withdrawn/suppressed records; never overwrite existing contacts from an unverified request. Idempotency, concurrent request handling, abuse limits and retention required. Do not expose private tables or grant browser writes. Review design with actual schema first.
3. Implement verified control of each destination using expiring single-use cryptographically random tokens with hashed storage, separate channel binding and replay protection. Generic public responses; no identity enumeration. Do not confirm merely because a request was submitted. Preference edits require verification, explicit new consent for additional topics and durable withdrawal history; suppressions cannot be bypassed. Unsubscribe must be simple and not require a login. Test anonymous/private read/write denial, invalid input, malicious text, concurrent duplicates, rate limiting, suppression, token expiration/reuse, consent immutability, no auto-subscription from inquiry, no send on draft. Use rolled-back/synthetic fixtures only. Live delivery tests require separate owner authorization; no provider activation or messages under this approval.

## Pending transaction draft — validation record
`supabase/admin-setup/phase-3c3-pending-draft.sql` adds a staged, private service-role-only function, not a public API. It derives consent wording/version server-side, checks nine approved active topics, requires affirmative adult and channel consent, uses one destination per call with an advisory transaction lock, never joins unverified email and SMS identities, preserves existing contact names/statuses and skips active suppressions. Duplicate requests do not append duplicate requested consent events. No confirmation, active opt-ins or provider calls are implemented. The draft was exercised on the existing schema inside an explicit rolled-back transaction with synthetic fixtures only; service-only grants, rejected invalid inputs, independent channels, pending status, deduplication, requested consent events, unchanged identity and suppression/withdrawal preservation passed. No migration applied. Actual concurrent execution, rate limits, expiring confirmation tokens, verified preference changes and public gateway integration are still required. Any future writer must coordinate suppression and destination locks; the lock is not a substitute for abuse prevention. Draft wording, launch policies and provider disclosures must be reviewed before real collection.

## Phase 3C.3B — confirmation and verified preference service draft
The private draft SQL files are not migrations to run on the live site. In a single isolated transaction load pending-draft.sql, confirmation-draft.sql, then confirmation-test.sql and ROLLBACK. Never log raw tokens or use real contact information. The tests have passed using the current HAG Administration schema and rolled-back synthetic data. No provider or public HTTP wrapper exists.

- 256-bit cryptographically random hex capabilities, SHA-256 hashes only at rest, purpose and destination bound, single use under destination lock. Confirmation snapshot limits changes to pending topics selected in that request. Confirmation/manage tokens expire after 30 minutes, edit tokens after 15 minutes, unsubscribe tokens after 60 days.
- Verified management returns only channel/topic/status and a single-use edit capability; explicit additions require adult declaration, current version and affirmative consent. Withdrawals append history. Existing active suppression cannot be cleared. Separate email/SMS identity and consent remain independent.
- Channel-wide unsubscribe via possession of a dedicated capability withdraws pending/active topics, sets durable suppression, invalidates outstanding confirmation/manage/edit capabilities, and is not blocked by ordinary redemption budget. Replayed tokens do not repeat writes.
- Database issuance budgets: 30/minute and 300/hour global, 3/15 minutes per destination (keyed HMAC bucket), redemption 120/minute shared for confirmation/manage/edit. Fixed windows permit boundary bursts and a shared cap can be exhausted by abuse. No IP-based limit yet. The future gateway must bound body size, malformed requests, trusted client/IP signals and invalid unsubscribe attempts; apply provider callback verification and operational monitoring. No account enumeration: raw issue results are exclusively for the trusted delivery adapter; public response must be generic regardless of existence/suppression/rate limit. Edit capabilities are handed to verified users only. Never expose delivery tokens via response, URL logs, analytics or referrers. Use explicit POST confirmation rather than state-changing GET; provide one-click unsubscribe compatible with applicable requirements after review.
- Draft tables force RLS and deny direct client access, including service role. Four private definer entrypoints are service-role-only; internal helper and old pending transaction execute are revoked from API roles. The trusted future server must protect service credentials and use a narrowly reviewed adapter, not expose a general SQL endpoint. All destination writers must share the lock protocol. No schema installation or production grant changes.
- Remaining release gates: actual multi-session concurrency/load testing, trusted gateway and its abuse controls, non-enumerating response/timing review, confirmation/preference UI and real browser tests, expiry/retention cleanup scheduling and privacy policy/consent/legal review; provider-specific signed SMS STOP/HELP handling, real destination delivery and operational opt-out acceptance require later explicit approval. No channel is ready for public collection or sending yet.

## Phase 3C.3C — isolated gateway draft
No deployed HTTP route or provider. Browser preview builds the same request envelopes as the gateway test harness but never transmits them. The server-side handler accepts only HTTPS POST JSON and restricted CORS preflight from the exact H.A.G. origin, no query string, maximum 8 KiB streamed body and 2-second read deadline. Unknown fields/actions, stale consent version, invalid token/topic/channel/adult/consent are rejected. Origin checks are not authentication or bot protection; token possession is required for verified operations. Responses are no-store and issue outcomes are generic, including unknown destinations, duplicate keys, throttling and backend/delivery failure. Timing differences remain unmeasured; do not claim timing indistinguishability.
The simulation accepts only reserved fictional destinations (.invalid email and NANP 555-0100 through 0199). Its bounded in-memory capture is for tests only; raw delivery tokens are not returned by public issuance responses. A verified manage redemption returns only scoped topic/status and edit token. No real transport. The PostgreSQL adapter uses fixed parameterized SQL and needs an injected trusted server executor; there is no driver, production connection, or public RPC wrapper in this draft. Require a bounded pool, statement/lock deadlines, least-privileged runtime credentials, trusted runtime IP extraction and distributed ingress defenses before deployment.
Draft budgets: 40 requests/minute per canonical IP and 600/minute per process at ingress (bounded, includes malformed POSTs); database gateway 20/minute per keyed source, 240/minute shared ordinary traffic; separate opt-out source budget 20/minute. Prior issuance and redemption ceilings remain. Local ingress can still block opt-out under overload; production opt-out availability and edge protection need review. Fixed windows and shared ceilings permit bursts and denial of service; not a guarantee against abuse. No untrusted forwarded-header IP. No production runtime wiring.
The new private issue wrapper atomically claims a UUIDv4/channel key (retained one day) before issuance, never stores raw tokens or issues a second token for the same key, even when body changes. Separate channel operations can partially succeed. Retrying a lost issue response with the same key does not redeliver; fresh explicit request after cooldown is required, until a secure durable delivery/outbox design is reviewed. Earlier private issuance helpers are no longer callable by service_role directly. No migration applied.
SQL gateway tests passed in a rolled-back transaction against the existing schema. Run the pending, confirmation and gateway drafts, then gateway-test.sql, then ROLLBACK. The previous confirmation test runs separately before the gateway draft because it tests the older direct helper grants. HTTP tests use concurrent mock calls and the shared form envelope; actual independent PostgreSQL sessions, load/deadlock tests, integrated driver/runtime, verification UI, safe token handling, timing review and delivery/consent acceptance are outstanding. Keep PR #28 draft, unpublished and unmerged.
